# 文档调整记录

## 版本 v2.0 (2025-12-01)

### 调整背景

基于对 ANALYSIS.md、PROBLEM.md、DESIGN.md、PLAN.md 的全面审查，发现原方案过于激进，存在以下问题：

1. **向量检索和 LangGraph 都标记为 P0（必须立即实施）**，但同时启动风险极高
2. **缺少渐进式实施路线图**，没有明确的 MVP、优化、生产三阶段划分
3. **时间估算过于乐观**，LangGraph 迁移估计 6-10周，实际可能需要 10-16周
4. **PLAN.md 缺少关键内容**：数据库迁移策略、完整的技术指标、错误处理机制

### 核心调整策略

采用**渐进式开发**策略，分为三个阶段：

```
MVP 阶段 (0-2月)  → 优化阶段 (2-4月) → 生产阶段 (4-6月)
     ↓                    ↓                   ↓
  快速验证           提升质量              系统化
  召回率75%          召回率85%            召回率90%+
  无额外成本         $10-20/月            开源方案
```

## 关键决策点

### 决策1: 向量检索从 P0 降级为 P1
**理由**:
- MVP 阶段可以用增强的关键词优化作为过渡方案
- 召回率 75-85% 对于 MVP 验证已经足够
- 避免初期引入过多复杂度

**风险**:
- 召回率比向量检索低 10-15%
- 如果 MVP 验证时发现召回率不足，需要提前引入向量检索

**应对**:
- 在 MVP 阶段持续监控召回率
- 如果召回率 < 70%，立即启动向量检索

### 决策2: LangGraph 重构延后到生产阶段
**理由**:
- MVP 阶段保留现有架构，降低开发难度
- 现有架构已经过验证，稳定性好
- LangGraph 学习曲线陡峭，需要时间

**风险**:
- 现有架构性能可能不足（响应时间 > 60秒）
- 代码维护成本较高

**应对**:
- 如果 MVP 阶段性能成为瓶颈，可以在优化阶段提前引入 LangGraph
- 优先优化数据预处理和缓存，而非架构重构

### 决策3: 采用独立数据库（MVP 阶段）
**理由**:
- 不影响现有舆情系统
- 如果 MVP 失败，可以直接删除数据库
- 数据隔离，避免误操作

**风险**:
- 需要维护两个数据库
- 无法复用部分基础表

**应对**:
- 生产阶段评估是否需要合并数据库

## 总结

1. ✅ 1-2个月即可上线 MVP，快速验证可行性
